# Covenant: instructions for coding agents

Covenant is a Forge app for Atlassian's Codegeist 2026 hackathon, built by one developer at 10 to 15 hours a week.
Official deadline: Tue 22 Dec 2026, 12:00 PT. Target submission: 21 Dec 2026. Judging runs 5 Jan to 3 Feb 2027, so the app must keep working until then.

## What it does

A user attaches a contract (text PDF or DOCX) to a Jira work item and clicks Extract. Covenant pulls out the contract's obligations and shows each one with its verbatim clause and page. After a person reviews them, it creates child work items with due dates. Before a renewal notice window closes, it opens a decision item with a brief: the deadline and why, how to give notice with send-by dates and a drafted notice, the contract's value, the supplier's record against its service levels, and owners from Jira and Teamwork Graph. A certificate or report attached to an obligation's work item is checked against its clause. A Rovo agent (with a Rovo skill) and an MCP server expose the same four actions.

Build order since Phase 4 (from the Phases 4.5 to 4.7 plan of 15 Nov 2026): fixes, holiday calendars, one-click setup, drafted notice, send-by dates, money at stake and charts, clause to claim, why this date, trap suite and CI gate, injection hardening, evidence check, Rovo skill and Automation recipe, AI access log, quality panel. All fourteen steps are built and checked on both sites. Phase 5 (harden, clean-site test, release, video, Devpost) started 16 Nov 2026: hardening re-checked for the 4.5 to 4.7 code (size guard, rate limits, log audit, empty states) and every permission explained in `PRIVACY.md`; the clean-site judge run on a never-used site (`covenant-judge`, 16 Nov 2026) passed every README step, MCP included, after the fixes it found; the Automation recipe was checked on `one-atlas-ykdi`. Since then (16 and 17 Nov 2026): the register and `list_obligations` read each work item's Jira status (a done one-off is Done, never overdue; a done recurring duty shows its next date), a finished recurring work item's panel opens the next date's item on a click (`openNextWorkItem`, table `obligation_work_item`), old evidence checks have Check again, the notice item has Update the letter, model work is capped at 60 readings per site per day (`src/forge/budget.ts`), and the client moves to the fallback model by itself if Forge stops offering the production one. The video and the form are the developer's.

## Trust rules (these hold everywhere)

- The model only reads text and returns structured rules: kind, responsible party, anchor event, offset (number, unit, direction), recurrence, quote, page hint. It never returns a calendar date it worked out. A date the contract writes out (an effective date, a stated end date) may be copied as text from inside its verified quote; code parses it (`packages/core/src/dates/written.ts`) and sends blanks, two-digit years and ambiguous numeric dates to review.
- Deterministic code in `packages/core/src/dates` resolves rules into dates. It has unit and property-based tests.
- Every obligation's quote must appear verbatim in the source text after whitespace normalisation (`packages/core/src/verify.ts`). No match, no obligation.
- The page shown to users is derived by code from where the quote was found. The model's page is only a hint for choosing between repeats. So is the clause number ("clause 1.2 (Term and renewal)"): `packages/core/src/sections.ts` reads it from the text around the quote, stored in the `clause_section` table; older extractions are backfilled by the daily check (`src/forge/jobs/sections.ts`) by reparsing the file, with no model call.
- Low-confidence or conflicting clauses get a second pass. If the passes disagree, the clause is marked "needs review". Never guess.
- Nothing is written to Jira until a person approves it or clicks to create it.
- Never log contract text. Log ids, counts and timings.
- The model never totals money. It copies an amount as text from inside its verified quote; `packages/core/src/money.ts` parses it into minor units and does every sum. Notice addresses, contract values and evidence findings pass the same verbatim check as obligations.
- Contract text (and any document's text) is data, never instructions: clauses that read like instructions to an AI are flagged (`packages/core/src/injection.ts`), tool replies return contract text only in quote fields with `quotedText`, and tool descriptions say so.
- Every clause read through the panel, the agent or MCP goes in the access log (`src/forge/access.ts`): account id, time, channel, obligation id. Never text.
- An evidence check decides pass, fail or needs review in code (`packages/core/src/evidence.ts`); the model only lists requirements with quotes from both documents and copies any expiry date as text. Unreadable or doubtful means needs review.

## Layout

- `packages/core`: pure TypeScript, no Forge, Node or browser imports, never reads the clock or logs (enforced by `test/purity.test.ts`). Schema, verifier, date engine with holiday calendars (`dates/holidays.ts`), extractor (`extract.ts`, one prompt and the `record_contract` tool) and critic (`critic.ts`). The details pass (`details.ts`, tool `record_contract_details`, `DETAILS_VERSION`) reads parties, notice address and methods, value and service levels in a separate call so the extractor and its eval stay unchanged. Also `money.ts`, `notice.ts` (send-by dates, drafted notice), `sla.ts` (measuring service levels, credits, drafted claim, leverage), `evidence.ts` (`record_evidence_check`, `EVIDENCE_VERSION`, chase draft) and `injection.ts`. Model calls go only through the `LlmClient` interface (`llm.ts`), which also holds `PRODUCTION_MODEL`. Bump `EXTRACTOR_VERSION` (now 2), `DETAILS_VERSION` or `EVIDENCE_VERSION` when that prompt, tool or its checks change.
- `src/parse`: attachment bytes to page text (PDF via `unpdf/pdfjs`, DOCX via mammoth). No Forge imports.
- `src/forge`: resolvers, queue consumer (extraction, details and evidence jobs, by `mode`), scheduled trigger, the attachment trigger (`pipeline/evidence.ts`), the four actions, SQL repositories, Teamwork Graph client, `details/service.ts` (notices, value, supplier record, claim and notice items), `admin/setup.ts` (one-click setup) and `access.ts`. `src/forge/spikes` is Phase 0 throwaway code.
- `src/frontend`: UI Kit screens.
- `src/forge/tools`: the four Rovo/MCP actions (`list_obligations`, `get_clause`, `get_renewal_brief`, `record_decision`). Input rules live in `packages/core/src/tools.ts`. The agent prompt is `resources/agent/prompt.txt`; the agent's Rovo skill is `skills/covenant-renewal-review/SKILL.md` (`rovo:skill`, Preview); the outside-agent skill is `skills/covenant-contracts/SKILL.md`; judge setup steps are `docs/mcp.md`; the Automation recipe is `docs/automation.md`.
- `src/forge/llm`: the production `LlmClient` over Forge LLMs. It must call the model exactly as `eval/src/anthropic-client.ts` does: same model id, temperature 0, one forced tool, same repair wording.
- `eval/`: a workspace that scores `packages/core` against 30 CUAD contracts and writes `eval/report.md`, and runs 20 invented trap contracts (`eval/src/traps.ts`, report `eval/traps.md`). `eval/baseline.json` holds the scores CI must not fall below (`--gate`); raise it by hand after a better run. CUAD files live in `eval/data/`, which git ignores. They never go in git or in the app. Tune prompts on the dev split only (`--dev`).
- `samples/fictional`: invented contracts and certificates for tests and demos.
- `docs/spikes.md`: spike results (Phase 0, S7 attachment event, S8 agent assignment).

## Platform facts (checked on developer.atlassian.com, 11 Nov 2026)

- UI functions time out at 25 s; actions and rovo:agentConnector at 55 s; queue consumers and scheduled triggers default to 55 s and allow `timeoutSeconds` up to 900. Extraction runs in a queue consumer; the Rovo/MCP Extract tool must enqueue, not run inline.
- One `llm` module and one `rovo:mcp` module per app. Both, and `sql`, are declared from the first deploy because adding `llm` or `sql` later forces a major version.
- Forge LLMs: `@forge/llm` `chat()`; no JSON mode, so structure is forced with one tool plus `tool_choice`. Tool arguments are JSON strings in both directions even though the SDK types say object (spikes S2, S2b); a replayed assistant tool call also needs `content: []`, because `''` becomes an empty text block that the API rejects. The only Haiku is `claude-haiku-4-5-20251001`, past its earliest retirement date; keep the model id in config with `claude-sonnet-4-6` as fallback, and record the model on each run. `ForgeLlmClient` asks `list()` at most every ten minutes and core's `chooseModel` keeps Haiku while it is listed (deprecated included), else the fallback. The models page (checked 17 Nov 2026) lists Haiku 4.5 as ACTIVE, retirement "not sooner than" 15 Oct 2026, and promises at least six months' notice of deprecation; it does not say what a retired model's call returns. The eval must use the same model id as production. LLM tokens have no free allowance and are billed to the developer.
- Forge SQL: no foreign keys, no transactions, one statement per query, `?` parameters, SELECT 5 s, request 1 MiB, response 4 MiB. Migrations do not run on deploy: every entry point calls `ensureSchema()` (`src/forge/db/schema.ts`), and new migrations append to its one chain. `INSERT IGNORE` works and `rows.affectedRows` says whether a row went in (verified 12 Nov 2026), so idempotency is a unique key plus `INSERT IGNORE`, and state changes are conditional UPDATEs.
- `@forge/events` 3.x (3.0 only added TypeScript 5 support): events wrapped in `body`; 50 events or 200 KB per push, so pass ids, not text. A consumer that throws is redelivered for up to 24 hours, so the worker records failures on the run instead of throwing.
- Adding a scope is a major version: `forge deploy` stops until run with `--approve MAJOR_VERSION_RULE`, then each site needs `forge install --upgrade`. Consenting to scopes on a site is the developer's decision, not the agent's. Renaming an issue panel's key means re-adding it from the work item's View app actions menu.
- Teamwork Graph (Preview): `api.asUser().requestTeamworkGraph(query, variables, operationName)` only. Operation names are `covenant_<name>` (name 4+ chars). HTTP 200 can carry errors; missing scopes silently drop rows; page until `hasNextPage` is false; never call it from a scheduled or queued function. Client: `src/forge/graph/client.ts`.
  - Introspection (`__type`) works (12 Nov 2026). Fields Covenant uses: `jiraWorkItemGoals(id)` → `AtlassianGoal`, `atlassianTeamsBySpace(spaceAri)` → `AtlassianTeam`, `atlassianTeamMembers(teamAri)` → `AtlassianUser`, `jiraWorkItemComments(id, since)` → `JiraWorkItemComment`. Ids are ARIs: `ari:cloud:jira:<cloudId>:issue/<id>`, `ari:cloud:jira:<cloudId>:project/<id>`. Nodes are unions, so use inline fragments; `User` is an interface (`id`, `name`) and `AtlassianUser` adds `accountId`.
  - There is no curated field for linked work items or incidents: those come from Jira search, as the user.
  - Goals and teams return real data with the current scopes (spike S9, 15 Nov 2026): a goal counts once it is linked from the goal's Jira tab (or the work item's Goals field), and a team once its page links the Jira space (Team links, Add Jira space). Test data on `one-atlas-ykdi`: goal TIDRWDEA-34 on MOBL-63 and team "Covenant test: supplier management" on Mobile Dev.
  - Scopes are per object type: `read:graph:goal:atlassian`, `read:graph:team:atlassian`, `read:graph:issue-comment:jira`, `read:graph:project:jira`, plus the issue and user scopes.
- Dates people see use their calendar: `todayIn(timeZone)` in `src/forge/dates.ts`. The panel and register send the browser's zone; the tools take an optional `timeZone` input and echo the zone used; the daily job has no person and stays on UTC. Jira's `/rest/api/3/myself` (profile time zone) needs `read:jira-user`, which Covenant does not have, and `serverInfo.serverTimeZone` is the server's (`Etc/UTC`), not the user's (checked 13 Nov 2026).
- Personal data (checked 13 Nov 2026): Atlassian's user privacy guidelines require any app storing personal data, account ids included, to report them through the personal data reporting API (`privacy.reportPersonalData` from `@forge/api`, scope `report:personal-data`, at most once per 7-day cycle per account, 90 per request; it rejects with the raw response on anything but 200/204) and to erase closed accounts' data and refresh or erase changed ones. Covenant stores account ids only; `src/forge/jobs/privacy.ts` (run by the daily check) reports them, writes `erased` over closed ones, and purges expired context cache rows (the only place names live). Decision snapshots are depersonalised (`packages/core/src/privacy.ts`). Data an app erases proactively needn't be reported. Forge-hosted storage, SQL included, is soft-deleted on uninstall and deleted after the retention period; relinking is possible within 21 days.
- Attachments: `requestJira` bodies are `string | ArrayBuffer | URLSearchParams`. A hand-built multipart body passed as an `ArrayBuffer`, with `X-Atlassian-Token: no-check`, uploads intact (checked by SHA-256 after download, 12 Nov 2026).
- Pages: the admin page is at `/jira/settings/apps/<appId>/<envId>` and the global page at `/jira/apps/<appId>/<envId>`. A daily `scheduledTrigger` first runs within a day of deploy; the admin page's "Run the daily check now" runs the same code.
- rovo:mcp (Preview): tools are action keys; external access is off until a site or org admin enables it; endpoint `https://mcp.atlassian.com/forge/<appId>`. Spike S4: tools are listed as `<key>_development` outside production, so never hard-code tool names; the caller is `context.principal.accountId` (not in `payload.context`); `api.asUser()` works inside the action and runs as the caller.
- Actions and rovo:agent (checked 12 Nov 2026): `forge lint` rejects an action `description` over 255 characters (YAML `>` adds a newline that counts; use `>-`), so output shapes go in the reply itself, the agent prompt and the skill file. Input types are string, integer, number, boolean. Adding actions and a `rovo:agent` deployed as a minor version (4.1.0). In Rovo chat, a non-GET action shows a "Please review" card with the inputs before it runs. Teamwork Graph via `asUser()` works inside an action (`get_renewal_brief`, 2.3 s with context). The admin's app details page (Apps, Sites, site, Connected apps, View app details; in organisations whose Apps menu has no Sites, Apps, Atlassian apps, then "Looking for your Marketplace and third-party apps?", checked on `covenant-judge` 16 Nov 2026) has one TOOLS switch ("Expose tools to MCP-compatible apps") for all of an app's tools, so newly added actions are exposed without another click; the same page has the AI MODELS switch Covenant needs. An MCP client sees the action `description` as the tool description and each input's `description`, `title` and `type` as its JSON schema (`required` becomes the schema's required list); a YAML `>` description keeps a trailing newline, so use `>-`. A Claude app custom connector (Settings, Connectors, Add custom connector, then Atlassian OAuth) works as an outside client and passed the Phase 4 done-when on 12 Nov 2026.
- Anthropic API (eval only): `@anthropic-ai/sdk` 1.x sends API version 2026-10-21, which rejects `temperature`. Production runs Haiku 4.5 at temperature 0, so the eval pins SDK 0.137.0, the last release on 2023-06-01. `claude-haiku-4-5-20251001` is Active on the API at $1/$5 per million tokens (checked 12 Nov 2026).
- Attachment trigger (spike S7, 15 Nov 2026): `avi:jira:created:attachment` carries `attachment {id, issueId, projectId, fileName, createDate, size, mimeType, author}`, `atlassianId` and `selfGenerated`; uploads the app makes (even `asUser()`) are `selfGenerated: true`, so `filter.ignoreSelf: true` drops them. Needs `read:jira-work` only.
- `rovo:skill` (Preview, checked 15 Nov 2026): `source.dir` holds a `SKILL.md` whose `name` matches the folder; `dependencies.tools` and `allowed-tools` list action keys of the same app; the agent lists it under `skills`. It deployed as a minor version.
- Forge agents cannot be assigned work items (spike S8): the work-item surface is a Studio setting and Studio does not manage Forge agents. Jira Automation's agent action is the route (`{{agentResponse}}`). Checked end to end on `one-atlas-ykdi` 16 Nov 2026 (`docs/automation.md`): the action is now "Use agent" under Rovo AI in a "flow" (Space settings, Automation, Create flow); the first use asks to connect Atlassian Automation to Rovo, after which the agent runs with the connecting person's permissions while the comment is posted by Automation for Jira; the smart values condition has no "is not empty", so use "does not equal" with an empty second value.
- One-click setup needs `manage:jira-configuration` (create project, issue type, scheme). Added 15 Nov 2026 (development major version 6). Since 17 Nov 2026 setup creates COVN from the task tracking template (`jira-core-simplified-task-tracking`): a spike on `one-atlas-ykdi` found it brings company-wide Task and Sub-task with To Do and Done, so work items finish in one step; setup still adds Contract, and adds Task or a subtask type only when the project lacks one. Before that, checked on `one-atlas-ykdi` 16 Nov 2026: it created COVN from the procurement template (statuses Requested, Approved, Purchased), which gets its own work type scheme ("COVN: Procurement Issue Type Scheme", no other project) holding only Order, so setup adds the site's Contract type (reused, not duplicated) and a company-wide Task type to that scheme; otherwise the sample's reviews and incidents would be Orders. A fresh site has no company-wide Task (its first team-managed space owns its own), so setup creates one, as it does Contract. Project names are unique: on `convenant10` (production 4.1.0, 16 Nov 2026) an existing "Contracts" project made setup fail until it learned to fall back to "Contracts (Covenant)", then "Covenant contracts". After the Task fix, setup created a company-wide Task there next to the space's own, and the current samples loaded into COVN as Contract items with Task related work, all quotes verified. The clean-site run on `covenant-judge` (production, 16 Nov 2026) found COVN had no subtask type either: Approve failed with "no work type that can sit under a Contract", and the daily check's Decision due items and the notice and claim items would have failed the same way. A fresh site's only Subtask types belong to its team-managed spaces, so setup now adds the site's company-wide Subtask or creates one (`hierarchyLevel: -1`, which needs Administer Jira); clicking setup again repairs a project set up before. A second click changes nothing.
- UI Kit `BarChart` needs `@forge/react` 11.2 or later; `User` renders an account id as a name in the browser, so names are never stored.
- unpdf's main entry cannot be bundled by Forge (it calls `import.meta.resolve('pdfjs-dist/...')`); import `getDocument` from `unpdf/pdfjs` instead.

## How to work

- One phase at a time from the build plan. Before coding, restate the phase's "done when" and list the files you will touch.
- Write tests first for anything in `packages/core`.
- Keep each change small enough to deploy and try, and give the exact commands.
- Before using any Forge module, package or API, check its current page on developer.atlassian.com and report what you found. If unsure something exists, write a small spike instead of guessing.
- If something is impossible on Forge, stop and say so, with the closest alternative.

## Commands

```
npm run check                      # type-check everything and run core and eval tests
npm test                           # core, eval and app tests (test/: Forge code with Jira, SQL and graph faked)
npm run eval                       # score 30 CUAD contracts with the production model; needs ANTHROPIC_API_KEY and eval/data/cuad
npm run eval -- --dev              # 10 separate contracts for prompt work
npm run eval -- --rescore <file>   # rebuild the report from a saved run, no model calls
npm run eval -- --gate             # also fail if scores are below eval/baseline.json
npm run traps                      # the 20 trap contracts; --gate, --only <id>, --break (prove the gate)
npm run samples                    # rebuild the fictional sample PDF and DOCX and verify their clauses
npm run spike:local -- <file>      # local fingerprint of a PDF or DOCX, to compare with spike S1
forge deploy -e development
forge install --upgrade --site <site>.atlassian.net --product jira
forge logs -e development
```

## Do not build

Amendments or amendment precedence, the Teamwork Graph connector, OCR, Confluence or Jira Service Management screens, Marketplace licensing, a vector database or retrieval pipeline, an agent framework, `rovo:agentConnector`, custom JQL functions, Realtime, Containers, or anything that calls an external service or host from the deployed app. The model never totals money.
